# -------------------------------------------------------------------------
# ACAS - Applewood Computers Accounting System
# COBOL -> Python 3.12 migration of the batch posting cycle
#
# WHAT A LOCK FILE IN THIS MIGRATION IS
#
#   pyproject.toml is the AUTHORITATIVE manifest: it declares the
#   interpreter
#   floor and ceiling, the packaging rules, the three dependency sets and
#   the
#   test-runner configuration. The three lock files mirror its three sets
#   in
#   flat, hash-verified form, for environments without a build backend
#   and for
#   container builds that must install under `--require-hashes`.
#
#   There are three files, one per set, and the sets are PAIRWISE
#   DISJOINT:
#
#     requirements.txt          [project].dependencies
#                               the shipped
#                               runtime set
#     requirements-harness.txt  [project.optional-dependencies].harness
#                               layered on
#                               top of requir
#                               ements.txt
#     requirements-dev.txt      [project.optional-dependencies].dev
#                               the
#                               verification
#                               toolchain,
#                               standalone
#
#   A version that differs between pyproject.toml and its lock file, or a
#   package that appears in a set it does not belong to, is a defect.
#
#   ONE PIN IS DELIBERATELY ABSENT FROM THIS FILE, AND ITS ABSENCE IS NOT
#   DRIFT. The build backend - setuptools, pinned exactly in pyproject.toml's
#   [build-system] requires - is a BUILD requirement, not a runtime
#   distribution of the migrated cycle. It is resolved into the isolated build
#   environment by the build frontend and is never imported by any acas_posting
#   module, so installing it into a run-time environment would add a
#   distribution the cycle does not use. requirements-dev.txt carries its
#   hashed entry instead, so the backend can be installed under hash
#   verification and the wheel then built with `--no-build-isolation`. Every
#   pin listed BELOW is a distribution the cycle actually imports, and that set
#   is what must reconcile pin-for-pin with pyproject.toml's
#   [project].dependencies.
#
# WHY THE HASHES ARE HERE
#
#   Every requirement carries `--hash=sha256:` entries for every artifact of
#   its pinned version that CPython 3.12 can install - each platform wheel
#   plus the source distribution. Passing `--require-hashes` then makes pip
#   refuse any artifact whose content does not match, which turns the pins
#   from a statement of intent into an enforced one: a compromised or
#   substituted index cannot serve different bytes under the same version
#   number.
#
#   The digests were read from the package index metadata for each pinned
#   version, not transcribed by hand.
#
#   Install with:  pip install --require-hashes -r <this file>
#
#   See README-python-migration.md for how to build the comparison oracle,
#   seed a scenario, run both cycles and diff the resulting table state.
#
# WHAT A LOCK FILE IN THIS MIGRATION IS NOT
#
#   It is not a manifest for the COBOL system. The COBOL tree (common/,
#   copybooks/, general/, sales/, purchase/, irs/, stock/), the generated
#   MySQL bridge (common/*MT.scb, common/*MT.cbl) and the schema
#   (mysql/ACASDB.sql) are FROZEN specification sources: read
#   exhaustively,
#   never modified. The compiled comparison oracle under harness/ needs a
#   container toolchain - GnuCOBOL 3.2, MariaDB 10.11.7, MariaDB
#   Connector/C
#   3.3.4, the JC preSQL translator - declared in harness/Dockerfile.*.
#   Those
#   versions must never appear in a Python lock file.
#
# TARGET RUNTIME
#
#   CPython 3.12, enforced by pyproject.toml's `requires-python =
#   "==3.12.*"`.
#   Its decimal module is backed by the C libmpdec extension rather than
#   the
#   pure-Python fallback, which matters for both correctness and speed,
#   because
#   every monetary and quantity operation in the migrated cycle passes
#   through
#   decimal.Decimal. Python 3.13 and newer are rejected by design: no
#   parity
#   evidence against the compiled oracle was captured there.
#
# DO NOT UPGRADE
#
#   The versions were resolved on the build host, not recalled. Do not
#   upgrade,
#   downgrade or "check for newer": a driver or runtime change can move a
#   stored penny, and the only acceptable proof of equivalence is an
#   empty
#   scenario diff against the compiled COBOL oracle.
# THIS FILE - THE SHIPPED RUNTIME SET
#
#   Mirrors [project].dependencies. This is the minimum the migrated
#   cycle
#   itself needs: an AST import census over every .py file in the
#   repository
#   records that acas_posting/ imports exactly ONE third-party top-level
#   module - `mysql`, in acas_posting/dal/connection.py. SQLAlchemy is
#   pinned
#   because the Agent Action Plan section 0.5.1 names it as the permitted
#   Core-level access path; greenlet and typing_extensions are
#   SQLAlchemy's own
#   requirements, not choices of this migration.
#
#   PyYAML is NOT here. It belongs to the harness set: it is imported
#   only by
#   harness/dump_tables.py and harness/diff_states.py, lazily, inside the
#   function that reads a scenario file. See requirements-harness.txt.
# -------------------------------------------------------------------------
